# Phase 8 Plan 04: quote-request and review-reply Summary

Two new workflows, each with a webhook lane that creates a draft through the API and mails the owner a notice, plus a tenant-looping lane that mails only approved drafts and then marks them sent.

## Commits
- 6ac4cbf feat: quote-request and review-reply workflows (both JSONs plus the catalog test change; test edited first, see RED below)

## What was built
- quote-request: `POST /webhook/quote-request` (responseNode). The Normalize node validates tenant_id (UUID) and requires email_text or request. Its error output goes to a 400 reject. `POST /quotes` (120 s timeout) gets an explicit body, so tenant_id is stripped. The reply is `{draft_id,status,deduped}`. A non-deduped pending or needs_human draft goes through `/tenant/me`, a require-owner check, and a mail to the owner: "Quote draft #id waiting for approval", id only.
- review-reply: `POST /webhook/review-reply`. Validates rating 1-5 and platform google|tripadvisor|other, then `POST /reviews/draft`. The owner mail holds reply_text, or the violation codes when the draft is needs_human.
- Sender lanes (Schedule `*/15` for quote, hourly for review, each with a Manual twin): `GET /admin/tenants` (the only X-Admin-Key use) -> Split(1) -> Check key -> `/tenant/me` -> `GET /drafts?status=approved&kind=...` (alwaysOutputData) -> Filter (quote: contact_email and email_text present; review: reply_text present) -> mail (onError continueRegularOutput) -> "Mail ok" Filter (mailpit `ID` exists) -> `POST /drafts/{id}/sent` (onError continueRegularOutput) -> single `Loop end` -> Split. The quote mail goes to contact_email. The review mail goes to the owner as final text to paste. Nothing is ever posted to a review platform, and there is no review fetcher in the repo: the scheduled lane only polls approved drafts.
- Key headers are `={{ JSON.parse($env.TENANT_API_KEYS)[<tenant id expr>] }}` inline; no key enters item JSON. Both workflows set `saveDataSuccessExecution: none` and `errorWorkflow: error-handler`.

## Decisions and notes
- The mail node uses continueRegularOutput followed by a "Mail ok" Filter, not continueErrorOutput. A second path into `Loop end` would make it fire twice per iteration, which risks double-advancing Split In Batches.
- The webhook-lane "Needs approval" Filter deliberately has no alwaysOutputData, so a deduped draft cannot trigger a mail.
- Delivery is at-least-once (T-08-04-04): a crash between mail and `/sent` re-sends on the next run.
- The webhook trust posture is unchanged (internal port; the caller picks the tenant).
- The stale `daily-report` workflow remains on the existing branch n8n volume (import does not delete); `n8n unpublish:workflow --id=daily-report` or `make g-reset` clears it.
- The workflow JSONs were generated by a throwaway script in the scratchpad (not committed); the JSONs are the source of truth.
