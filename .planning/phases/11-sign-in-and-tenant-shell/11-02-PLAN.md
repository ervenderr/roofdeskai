`dashboard/lib/session-actions.ts` ("use server" at top, per locked decision "login is a server action"):
- `export async function signIn(form: FormData): Promise<void>`: `const key = String(form.get("key") ?? "").trim()`. If empty or longer than 256 chars, `redirect("/login?error=1")`. `const r = await checkKey(key)`. If `r === "bad"` redirect `/login?error=1`; if `"down"` redirect `/login?down=1` (no cookie in either case, AUTH-02). Otherwise build `Session` `{ kind: r.kind, key, name: r.name, modules: r.modules, exp: Math.floor(Date.now() / 1000) + SESSION_MAX_AGE }`, `seal` it with `process.env.SESSION_SECRET ?? ""`, and `(await cookies()).set(SESSION_COOKIE, token, { httpOnly: true, sameSite: "lax", secure: !local, path: "/", maxAge: SESSION_MAX_AGE })` where `local` is true when `(await headers()).get("host")` starts with `localhost` or `127.0.0.1` (locked: Secure when not on localhost). Then `redirect("/")`. Always redirect to the fixed path "/" (no `next`/returnTo parameter: no open redirect). Do not wrap `redirect()` in try/catch (it throws by design). A fresh sealed token is set on every sign-in, replacing any prior cookie.
- `export async function signOut(): Promise<void>`: `(await cookies()).delete(SESSION_COOKIE)` then `redirect("/login")` (AUTH-05).
- Never log or return the key.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> signIn server action | pasted key and form body are untrusted |
| Next server -> browser | rendered HTML and client chunks must never carry the key |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-08 | Information disclosure | cookie theft via XSS | mitigate | `httpOnly: true` so JS cannot read rd_session; payload is AES-GCM encrypted (plan 01); React escapes rendered strings |
| T-11-09 | Information disclosure | key in HTML/JS/URL | mitigate | key travels only in the POST body of the server action and inside the sealed cookie; login input is type=password with no defaultValue; redirects carry only error/down/expired flags; `.next/static` grep gate for key-shaped strings |
| T-11-10 | Information disclosure | cookie sent over plain HTTP | mitigate | `secure` set whenever host is not localhost/127.0.0.1 |
| T-11-11 | Spoofing | open redirect after login | mitigate | signIn redirects only to the fixed path "/"; no next/returnTo parameter is read |
| T-11-12 | Spoofing | session fixation | mitigate | no server-side session id exists; each sign-in mints a fresh sealed token that replaces any prior cookie |
| T-11-13 | Spoofing | brute-force key guessing through /login | accept | tenant keys are 256-bit `token_urlsafe(32)`; the login adds no surface beyond calling the API directly with the same headers; local-only this phase. Risk: the admin key must be high-entropy before any deploy (flag in SUMMARY) |
| T-11-14 | Tampering | CSRF on sign-in/sign-out | mitigate | Next server actions reject cross-origin POSTs (Origin vs Host check) and SameSite=Lax cookie; sign-out CSRF impact is only a forced logout |
| T-11-15 | Information disclosure | user enumeration via error text | mitigate | one identical error for wrong, revoked and malformed keys; API returns the same generic 401 |
| T-11-16 | Information disclosure | admin key exposure | mitigate | admin key never in dashboard env; it is only accepted from the login form and stored sealed; README no longer passes ADMIN_API_KEY |
</threat_model>
