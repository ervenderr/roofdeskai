<decisions>
## Implementation Decisions

### make new-business (OPS-01)
- **D-01:** `make new-business PACK=<slug>` runs `scripts/new_business.py`: (1) validates the pack via `load_pack`, failing with the pack error text; (2) registers/loads it as a tenant on the branch stack (idempotent, reuse existing tenant creation and FAQ seed code); (3) runs a smoke subset of evals for that pack, including cross-tenant retrieval and escalation scenarios, via the existing `evals.runner --pack` machinery; (4) exits non-zero on any failure. Never touches the live DB or pushes. Key minting is printed as a hint, not automated.
- **D-02:** Smoke subset selection is data-driven (categories `escalation`, cross-tenant/injection ids). A pack without those fails with a clear "pack has no escalation scenarios" error rather than passing silently.

### PII masking (OPS-03)
- **D-03:** Pure `mask(text) -> str` (email and phone regexes; unit cases for near-misses, unicode, multiple per string, already-masked), reusing `api/app/engine/pii.py` if suitable. A `logging.Filter` beside `TenantFilter` in `logctx.py` masks `record.msg` and `args` on the root handlers. Masking never raises (fails closed to a placeholder). Stored data is not altered.

### Retention and delete_subject (OPS-04)
- **D-04:** `RETENTION_DAYS` env (default 0 = keep). Purge deletes, per tenant under `db.tx(tenant_id)`, rows older than the cutoff across all PII-bearing stores (conversations/messages, leads, past appointments, drafts, intake_people, agent_events PII fields, tool logs, capacity_flags, brief_runs). FAQ, slots and tenants are config and never purged. Exposed as admin endpoint `POST /admin/retention/run` (super-admin, optional tenant) and as a script.
- **D-05:** `delete_subject(tenant_id, email|phone|external_id)` removes one person's rows across every store, returns counts per store, writes one audit row with no PII (identifier hash only). Tenant key for own tenant; admin for any. Tests prove other people and tenants are untouched. A coverage test introspects every table with `tenant_id` and requires each to be listed as purged or kept-with-reason.

### SOPs and runbook (OPS-02)
- **D-06:** `scripts/gen_docs.py` renders one SOP per workflow and one runbook per pack from pack data and the n8n workflow JSON into `docs/generated/<pack>/`. Use `string.Template`/`str.format`, no new dependency unless templates clearly need loops. A drift test regenerates into a temp dir and compares; `make gen-docs` rewrites. Output deterministic (sorted, no timestamps).

### Grep gate (OPS-06)
- **D-07:** pytest plus `make check-shared` greps `roof|Summit|Denver` (case-insensitive) in shared code (`api/app`, `n8n/workflows`, `prompts`, `scripts`, `evals` runner code, shared dashboard code). Excludes `businesses/`, `clients/`, `tests_data/`, docs, planning, eval scenario data and RoofDesk-own outbound/intake/pilot modules, each with a stated reason. Run the gate first to see the real hit list; fix trivial hits by moving to pack/config only when prompt render and pack hashes stay byte-identical, otherwise allowlist with justification.

### Data map (OPS-05)
- **D-08:** `docs/data-map.md`, factual from code: stores (Postgres tables, logs, n8n execution data, SMTP/mailpit, Ollama, pgvector), processors (LLM providers in the chain incl. hosted/cross-border, SMTP, n8n), retention behaviour, caveats (dental data is synthetic demo only pending legal review under GDPR Art. 9 / nFADP, cross-border transfer, n8n licence). A test checks every `tenant_id` table appears in the map. No legal conclusions beyond "needs review".

### README (OPS-07)
- **D-09:** README gets a per-business scorecard (from committed `evals/reports/` per pack, plus module eval counts) and a workflow catalog (from `n8n/workflows/`), generated by `gen_docs.py` between marker comments and covered by the drift check.
